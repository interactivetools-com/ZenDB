# Foreign Key Names Matrix

How every supported database server names foreign keys, and whether `Table::foreignKeys()` and `Table::foreignKeysReferencing()` report them correctly when two keys share a name. Generated by the "FK Names Matrix" workflow (.github/workflows/fk-names-matrix.yml); regenerate with:

    gh workflow run fk-names-matrix.yml   # wait for the run to finish, then:
    gh run download --dir probes          # pick the latest FK Names Matrix run
    php .github/scripts/fk-names-probe.php --merge probes/*/fk-probe-*.json > docs/internal/fk-names-matrix.md

MariaDB 12.0, 12.1 and 12.2 aren't in db-matrix.json. To include them, do a second run with `-f databases="mariadb:12.0 mariadb:12.1 mariadb:12.2"` and pass both runs' JSON files to --merge.

Last generated: 2026-11-10 from 22 servers. Generated file - don't hand-edit. The "Findings" list below is maintained in the heredoc in .github/scripts/fk-names-probe.php; edit it there.

## Findings

- MariaDB 12.1+ only needs a foreign key name to be unique within its table, and names unnamed keys `1`, `2`, `3` in every table. MariaDB thru 12.0 and every MySQL/Percona need the name to be unique in the database and name unnamed keys `<table>_ibfk_1`, `<table>_ibfk_2`. MariaDB's announcement: [Per-table unique FOREIGN KEY constraint names - new feature in MariaDB 12.1](https://mariadb.org/per-table-unique-foreign-key-constraint-names-new-feature-in-mariadb-12-1/) ([MDEV-28933](https://jira.mariadb.org/browse/MDEV-28933)). A request to go back to the old generated names was closed as Won't Fix ([MDEV-37592](https://jira.mariadb.org/browse/MDEV-37592))
- On MariaDB 12.1+, a second table in the same database can use a name another table already has, whether the server generated it or the CREATE TABLE gave it. Every other server refuses the second table (error 1022 on MySQL/Percona 5.7, 1826 on MySQL/Percona 8.0+, 1005 on MariaDB thru 12.0). The same name twice in one table is error 1061 on every server
- On every server, a foreign key in another database can reference a table in this one, and it can have the same name as a key in this database. Two unnamed keys get the same generated name when their tables have the same name
- `KEY_COLUMN_USAGE` rows for same-named keys come back in no fixed order under `ORDER BY CONSTRAINT_NAME, ORDINAL_POSITION`: the same query run twice on one server returned the two tables in a different order
- `ALTER TABLE ... DROP FOREIGN KEY <name>` only drops that table's key on every server, so a shared name is safe to drop by
- `DROP TABLE` on a table that a foreign key references is refused with a different error on each server family: 1217 on MySQL/Percona 5.7, 3730 on MySQL/Percona 8.0+, 1451 on every MariaDB. A key in another database blocks the drop the same way. Only the 3730 message names the key and its table, and it leaves out the database. A table referenced only by its own key drops without an error
- `Table::foreignKeys()` reads one table at a time and is correct on every server, with the right ON DELETE and ON UPDATE rules. `refDatabase` names the other database when a key references a table there
- `Table::foreignKeysReferencing()` groups rows by database, table, and name, and returns a plain list with a `database` field, so same-named keys each get their own entry. ZenDB 1.0.0 grouped by name alone and returned one entry for both: wrong on MariaDB 12.1+ for two tables in one database, and on every server for a key in another database
